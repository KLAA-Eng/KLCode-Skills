# Glossary entries

One canonical owner for a concept. Use a name the domain owner recognizes; distinguish overloaded meanings rather than merging them because code uses the same label.

## <Term>
Definition: concise meaning and scope.
Relationships: how it connects to other defined concepts.
Examples and non-examples: cases that reveal boundaries.
Evidence: relevant contract, source behavior or confirmed domain-owner statement.
Open ambiguity: needs confirmation, with the choice not yet made.

Definitions capture meaning, not task schedules, implementation details or full requirements. Cross-link a durable architecture decision rather than copying its rationale. When a definition changes, review dependent terms and the code/contracts that could become misleading. Do not create an empty glossary solely to satisfy a workflow.
